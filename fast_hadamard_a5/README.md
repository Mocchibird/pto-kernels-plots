# Fast Walsh–Hadamard (N=256) PTO-ISA on Ascend A5

Benchmark results for the PTO-ISA `fp16` fast Walsh–Hadamard transform kernel
[`fast_hadamard_256_a5`](https://github.com/huawei-csl/pto-kernels/tree/master/examples/jit_cpp/fast_hadamard_a5)
on an Ascend 950 / A5 (dav-c310) vector core.

The N=256 Walsh–Hadamard transform is a **memory-bound** streaming op: each row is
read once, transformed, and written back. The kernel uses a **deinterleave-load
butterfly** — every `log2(256)=8` stage performs the even/odd split on the MTE2
load (`vlds DINTLV_B16`) and the concat-halves recombine on the MTE3 store, so
only `vadd`/`vsub` touch the vector-execute pipe. The transform therefore runs at
essentially DMA speed, and the natural reference is a plain GM→UB→GM **copy**.

The benchmark sweeps **batch size** (`2^10 … 2^18` rows of 256) against the UB
tiling knob **`ROWS_PER_TILE`** (`NBUF` auto-fit to the 192 KB UB), at
`block_dim=64`. The plotted value is:

```text
had / copy = hadamard bandwidth / copy-floor bandwidth
```

Values near `1.0` mean the transform is running at the copy floor (optimal). The
copy floor is measured from a fixed, UB-valid `ROWS_PER_TILE=64` build, taking the
**median of 7 trials** per batch — this avoids the physically-impossible >HBM
readings a single timed loop can produce. Bandwidth is `(read + write) / duration`.

## Plots

### `hadamard256_grid.png`

![Fast Hadamard N=256: had/copy heatmap and bandwidth vs batch](hadamard256_grid.png)

Left: `had / copy` as a heatmap over batch size × `ROWS_PER_TILE` (red = slow,
green = at the copy floor), with the ratio printed in each cell. Right: absolute
bandwidth (TB/s) vs batch for the transform against the copy floor.

**What the plot shows:**

- The kernel sits **at the copy floor across essentially the whole grid** —
  `ROWS_PER_TILE ∈ {16, 32, 64, 128}` are all green once past the small-batch,
  launch-overhead region on the left. There is no meaningful speedup left to win;
  the transform is memory-bound and already DMA-limited.
- Absolute bandwidth climbs out of the ~launch-overhead floor and **saturates near
  ~2.8–3.0 TB/s** at large batch, tracking the copy floor the whole way.
- The only softening is the **batch = 64k column** (`had/copy ≈ 0.78–0.92`). That
  is where the *copy floor itself peaks* (~3.0 TB/s); the transform lags that
  single peak slightly but recovers by 128k–256k.
- `ROWS_PER_TILE` barely matters in the memory-bound regime — the default `64` is
  fine; `32` and `128` are comparable. (`ROWS_PER_TILE=256` single-buffers the
  pipeline and is excluded.)
- Correctness was verified separately: every `ROWS_PER_TILE` produces an identical
  result (rel err `8.5e-4` vs `x · Sylvester(256)`), and the copy reference
  preserves data bit-exactly.
